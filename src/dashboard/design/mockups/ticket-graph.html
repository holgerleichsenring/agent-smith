Mock only · what each element reads

  1. Card and pane: the push of kind tickets (SpecDialogProposalPush.tickets), each ticket's key, title, requirement, done items, requires and repositories, in TicketGraphOrderer order (2026-10-14-dbcej, 2026-10-14-dbcek). Keys are the identity; a list carries no spec ids.
  2. “nothing to wait for” is the proposal's own requires; whether an existing ticket like #41 has landed is read at filing (2026-10-14-dbcel), so the pane never says a ticket starts when filed.
  3. “waits for #41”: an existing ticket by its tracker key — #<id> when the id is numeric, as written otherwise (a Jira key).
  4. “required ticket not found” is the ITicketExistence finding (Azure DevOps' TF401232 included); filing refuses the whole list on it.
  5. The size / order / merge / missing findings come from the plan review (TicketPlanReview); a cut whose quote is verbatim in the ticket is applied by one re-prompt, the revised list is reviewed once more, and what that second review finds stands as findings. A size finding never splits a ticket: the keys are the identity.
  6. “the list — missing” is a finding about the whole list (key the list): a requirement from the messages or the uploaded files that no ticket covers. The reviewer reads the uploads; a requirement met by a ticket:<id> or left for a later list is not missing.
  7. On Jira an existing ticket reads as written (PROJ-41); everywhere else a numeric id reads #41.
  8. In a ticket's conversation the list is not reviewed and the notice says where a list is filed; Approve is not offered and approval files nothing (2026-10-14-dbcel).
  9. In Slack and Teams the confirmation is the compact list — key, title, number of done items, waits-for — and points here for the full texts.
  10. The ticket's own conversation, opened after filing, keeps the files uploaded here: its approval carries this conversation's citations forward (2026-10-14-dbcel).
  11. Approve & file / Reject are the approval card's pair in a conversation bound to no ticket (DialogQuestionCard); the offered shape sends the partner round again as one ticket's series.
  12. List buckets (2026-10-14-dbcen) read GET /api/tickets: a filed ticket with no run is a row of bucket blocked (a requirement unmet, as the claim gate reads it) or filed; it leads the first page only, carries no series strip, attempt marks or cost, and names what it waits for by tracker key.
  13. Graph view reads GET /api/tickets/graph?project=: nodes with their state (merged / done by hand > running > blocked > ready > the list bucket), edges from the dependent; a node with a page opens it, a page-less one opens the requires panel with the act.
  14. Never-run page reads GET /api/tickets/{project}/{id} (a detail with no attempt) and GET /api/tickets/{project}/{id}/requires: header, what it waits for, what waits for it, the filed line by kind (a list ticket says its specs come with its first run) and the Work it out link; no runway, no tabs.
  15. Done by hand posts POST /api/tickets/{project}/{id}/landed-by-hand (runs.control, note required); every refusal (400, 404, 409, 503) is the server's sentence shown as is, and a 200 re-reads the page's requires and detail at once.
